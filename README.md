# 问数（AskData）

> 让不会写结构化查询语言的人，用中文问出数据库里的答案，并且能看到依据、能判断结果可不可信。

一个模块化的 **数据问答服务**：把"自然语言问题"变成"数据库查询"，跑出结果，并给出解释。
围绕它，还配了一整套自动评测与失败归因，用来回答一个关键问题——**它到底有多准，错在哪。**

---

## 这个项目解决什么问题

大语言模型不知道你的数据库长什么样。它只能根据"订单""金额"这些词去猜表名和字段名，
猜出来的语句语法正确、字段全是假的，一执行就报错。

所以真正的难点不是"让模型写查询"，而是：

1. **检索**——从几十张表里挑出该看的那 5 张
2. **索引**——给模型看到"华东区"在库里到底长什么样
3. **校验**——只读沙箱、超时、行数限制
4. **修复**——报错了把错误信息喂回去重写
5. **评测**——用执行结果比对判断对错，并归因

本项目把每一块都做成可替换的模块，因此每一块都能单独做对照实验。

## 快速开始

```bash
# 1. 生成演示数据库（24 张表，约 12.7 万行，固定随机种子）
python scripts/init_db.py

# 2. 看一眼库结构，并自测只读沙箱
python scripts/inspect_schema.py

# 3. 校验测试集：每条标准语句必须真的能跑通
python scripts/validate_golden.py

# 4. 跑评测：先用规则基线确认评测链路是对的
python scripts/run_eval.py --mode keyword

# 5. 问一个问题
python scripts/ask.py "2026 年 6 月每个大区的订单实付金额合计是多少？" --show-context

# 6. 单元测试
python -m unittest discover -s tests -v

# 7. 消融实验（每次只关一个模块，看指标掉多少）
python scripts/run_ablation.py

# 8. 检查模型上下文协议服务的七个工具
python scripts/mcp_smoke_test.py
```

### 接真实模型

```bash
# 1. 复制模板（Windows 用 copy，macOS/Linux 用 cp）
copy .env.example .env

# 2. 打开 .env，填三个值：OPENAI_API_KEY / OPENAI_BASE_URL / OPENAI_MODEL

# 3. 确认能聊上一句
python scripts/check_llm.py

# 4. 先跑 5 题看看，再跑全量
python scripts/run_eval.py --limit 5
python scripts/run_eval.py
```

`.env` 已经写进 `.gitignore`，不会被提交。密钥只存在于环境变量和内存里，
配置文件 `config/default.yaml` 里不出现任何密钥。

只需要 Python 3.10 及以上。核心链路**零第三方依赖**（数据库用标准库自带的 SQLite）。

### 支持的数据库

| 类型 | 驱动 | 状态 |
|---|---|---|
| SQLite | 标准库，零依赖 | 已验证（200 题评测就是跑在它上面） |
| MySQL / MariaDB | `pip install pymysql` | 已验证（真实 MySQL 5.7，5 万行数据） |
| PostgreSQL | `pip install psycopg2-binary` | 已验证（真实 PostgreSQL 16.4，5 万行数据） |

三种数据库共用同一套上层逻辑：检索、提示词、沙箱、评测都不变，只有连接器不同。

### 一键初始化

```bash
python scripts/setup.py
```

会问你选哪种库、填地址或连接串，然后：测试连接 → 列出表 → 生成数据字典模板 → 写好 `.env`。

非交互（适合脚本或容器）：

```bash
python scripts/setup.py --dialect mysql --dsn "mysql://user:pass@host:3306/shop" --yes
python scripts/setup.py --check     # 只检查当前配置
```

### 数据字典为什么是文件

客户的库通常是**只读**的，我们不能像演示库那样在里面建 `_meta_tables`。
所以字典放在 `data/schema_meta.yaml`，跟着项目走：

```yaml
tables:
  orders:
    description: 订单主表，一行一个订单
    columns:
      pay_amount: 实付金额（原价减优惠）
```

加载优先级：文件 → 库里的字典表 → 空。三步都兼容。

### 换客户不用改代码

把配置写进客户端的 `env` 就行：

```json
{
  "mcpServers": {
    "askdata": {
      "command": "python",
      "args": [".../scripts/serve_mcp.py"],
      "env": {
        "ASKDATA_DIALECT": "mysql",
        "ASKDATA_DSN": "mysql://reader:密码@10.0.0.5:3306/prod",
        "ASKDATA_DICT": "D:/askdata/schema_meta.yaml",
        "OPENAI_API_KEY": "客户自己的密钥",
        "OPENAI_BASE_URL": "http://内网GPU:8000/v1",
        "OPENAI_MODEL": "qwen2.5-32b"
      }
    }
  }
}
```

内网部署时把 `OPENAI_BASE_URL` 指向自己部署的模型即可，不依赖外部服务。

**已知局限**（全部如实记录，见 `docs/项目方案.md` 附录）：

- **检索在 24 张表规模下不提升准确率**：把 20.4 张表全塞进上下文是 92.00%，检索到 7.7 张是 92.50%，差在噪声内。
  它的价值是"同样的准确率下省 12 张表"，不是"更准"。
- **报错重写贡献为 0**：首轮成功率 99.5%，修复循环几乎从不触发。定位是"低成本的保险"，不是"被验证有效的模块"。
- **重排实现了但默认关闭**：重叠版 −1.00、交叉编码器版 −4.50、大模型版 +1.00（在噪声内），三版都不足以留下。
  交叉编码器掉点的机理已定位：它让 73.5% 的题目前两名种子发生变化，而图扩展正是从前两名出发的。
  为此专门做了一版**为交叉编码器重写的链路**（先扩展再精排 + 分数阈值 + 表数预算），结果 −6.00，更差——
  因为它把检索召回从 99.04% 压到 91.46%，结构上必需的连接表被排到了后面。
  **结论：相关性判断 ≠ 连接可行性判断，通用重排模型不适合这个任务。**
- 200 道题上执行准确率 **93.00%**（单表 98.75%、多表 90.00%、嵌套 87.50%），
  14 道错题里 8 道是"多输出一列 id"，按数据一致口径约 97%。
- 只有 3 组消融（图扩展 −6.50、只给 3 张表 −10.00、关取值索引 −3.00）的差值显著超出噪声。

这些不是"没做完"，而是**实验得出的结论**——知道方案边界在哪，比报一个漂亮数字更重要。

## 设计上的三个选择

1. **用 SQLite，不用别的数据库**——标准库自带、零安装；而且它提供授权回调，可以在引擎层面拒绝写操作。
2. **自己写向量索引，不用向量数据库**——几十张表的规模下，暴力计算已经足够；而且"向量检索就是归一化点积排序"这件事，自己写一遍才讲得清。
3. **评测用执行结果比对，不用字符串比对**——同一个结果有无穷多种写法，字符串比对会把正确写法判错。
