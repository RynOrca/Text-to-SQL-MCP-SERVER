## 0. 一页纸

| 项 | 内容 |
|---|---|
| 项目名 | 问数（AskData） |
| 一句话 | 让不会写结构化查询语言的人，用中文问出数据库里的答案，并且能看到依据、能判断结果可不可信。 |
| 三个形态 | 命令行 → 模型上下文协议服务 → 可视化面板 |
| 技术约束 | 零第三方依赖（仅 Python 标准库 + 已装好的模型上下文协议开发包），全离线可跑 |
| 交付物 | ①可运行代码 ②自动评测报告 ③`.teach` 教学文档 ④演示录屏 |
| 目标岗位 | 大模型应用开发 / 智能体开发 / 数据智能方向实习生 |
| 周期 | 4 周（可压缩到 2 周，见第 10 节） |

## 1. 为什么做这个项目

### 1.1 岗位能力映射

目标岗位职责的六条里，这个项目直接覆盖五条：

| 岗位职责 | 项目落点 |
|---|---|
| 参与智能助手、内容生成、知识问答、办公提效等功能开发 | 数据问答本身就是"知识问答"的一个分支：知识不在文档里，而在数据库里 |
| 参与提示词设计、模型调用及效果调优 | 提示词组装、模型选型、温度与重试策略 |
| 参与知识库及检索增强生成应用开发，包括文档处理、知识检索、结果优化 | 检索对象从"文档段落"换成"表结构、字段取值、历史问答"，是本项目最大的技术块 |
| 参与智能体及智能工作流功能开发，学习任务编排、工具调用、上下文管理 | 整个项目就是一个工具调用型智能体：检索 → 生成 → 校验 → 执行 → 修复 |
| 参与大模型接口、业务系统接口及相关工具的对接 | 数据库就是业务系统；对外暴露模型上下文协议接口 |
| 参与应用功能测试、效果评估及问题分析 | 执行准确率、检索召回率、失败归因，全部自动化 |

### 1.2 三个"别人没有"的点

绝大多数同类项目止步于"能生成一句结构化查询语言"。本项目的差异化在模型之外：

1. **执行准确率可自动判定**。对错由数据库裁决，不靠人看。这意味着每一次改动都能立刻得到数字。
2. **检索层是双层结构**：表级召回 + 外键图扩展，解决"语义最像的表往往不是该连接的表"。
3. **失败可归因**：区分"检索错"与"生成错"，并分别给出指标。

## 2. 用户与场景

### 2.1 主用户

- **一线运营**：想临时看个数，不想排队等数据组
- **产品经理**：验证一个假设，只需要一次性的查询
- **项目作者本人**：给自己搭一个能随时问数的入口

### 2.2 三类典型问题（对应三个难度）

| 难度 | 示例 | 考察点 |
|---|---|---|
| 单表 | 上个月一共有多少笔订单？ | 时间过滤、聚合 |
| 多表连接 | 华东区新客的复购率是多少？ | 表选择、连接路径、指标口径 |
| 嵌套 | 复购率最高的三个类目是哪三个？ | 子查询、排序、分组 |

### 2.3 明确不做的事

- 不做通用数据库管理工具（不提供增删改）
- 不做报表平台（不做定时任务、不做权限体系）
- 不做多轮复杂对话（第一版只支持单轮 + 一次澄清）
- 不追求公开榜单排名（追求"每一层都讲得清"）

## 4. 总体架构

```
                        ┌──────────────────────────────┐
   用户提问 ───────────▶ │  接口层                       │
                        │  命令行 / 模型上下文协议 / 面板 │
                        └──────────────┬───────────────┘
                                       ▼
                        ┌──────────────────────────────┐
                        │  编排层（智能体循环）          │
                        │  澄清 → 检索 → 生成 → 校验     │
                        │  → 执行 → 修复 → 解释          │
                        └──────────────┬───────────────┘
              ┌────────────────┬───────┴────────┬────────────────┐
              ▼                ▼                ▼                ▼
      ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
      │ 检索层        │ │ 生成层        │ │ 执行层        │ │ 评测层        │
      │ 表级向量召回   │ │ 提示词组装    │ │ 只读沙箱      │ │ 执行准确率    │
      │ 关键字召回     │ │ 模型调用      │ │ 语法与权限校验 │ │ 检索召回率    │
      │ 倒数排名融合   │ │ 结构化修复    │ │ 超时与行数限制 │ │ 失败归因      │
      │ 重排          │ │              │ │              │ │              │
      │ 外键图扩展     │ │              │ │              │ │              │
      └──────┬───────┘ └──────────────┘ └──────────────┘ └──────────────┘
             ▼
      ┌──────────────┐        ┌──────────────┐
      │ 元数据层      │◀───────│ 数据层        │
      │ 表结构内省    │        │ 数据库连接器   │
      │ 数据字典      │        │ 演示库生成     │
      │ 取值索引      │        │              │
      └──────────────┘        └──────────────┘
```

### 数据流（一次问答的完整生命周期）

1. 用户提问
2. 口径检查：问题里的指标是否命中口径字典，命中则注入定义
3. 表级召回：向量召回 + 关键字召回，各取前 20 张表
4. 融合与重排：倒数排名融合，重排后取前 8 张
5. 图扩展：沿外键关系补一跳邻接表
6. 组装上下文：裁剪后的表结构 + 字段取值样本 + 相似历史问答
7. 生成结构化查询语言
8. 校验：语法、只读、白名单、强制行数上限
9. 执行，得到结果集或错误信息
10. 若报错，进入修复循环（最多 2 轮）
11. 生成一句话解释 + 返回结果表
12. 记录全链路追踪（每一段的输入、输出、耗时）

## 5. 六个关键设计决策

每个决策都按「问题 → 备选 → 决定 → 理由 → 代价」写。这部分是面试的主战场。

### 决策一：演示库用 SQLite，但连接器做成可替换的

- **问题**：选择什么数据库作为演示与分析对象。
- **备选**：DuckDB（分析型、快）、PostgreSQL（生产级）、SQLite（嵌入式、标准库自带）。
- **决定**：演示库用 SQLite；**对外交付时支持三种**（SQLite / MySQL / PostgreSQL）。
- **理由**：
  1. Python 标准库自带，**零安装**，教学文档可以让任何人十分钟跑起来。
  2. 提供**授权回调**（`set_authorizer`），可以在数据库引擎层面精确拒绝写操作。
  3. 但真实客户的库通常是 MySQL 或 PostgreSQL，所以连接能力被抽象成接口，
     三种数据库各实现一份，上层（检索、提示词、沙箱、评测）完全复用。
- **代价**：MySQL / PostgreSQL 各需要一份驱动依赖，且元数据查询语法不同；
  内省层因此从"直接读 SQLite 系统表"改成"通过连接器接口读"。

**后续补充（2026-11-07）**：已实现 MySQL 与 PostgreSQL 两个连接器，并用真实数据库端到端验证：
MySQL 5.7（建库、灌 5 万行、列/外键/行数/取值样本、只读防护、跨表查询全部通过），
PostgreSQL 16.4（同样 10 项全过，含五表自连接查询）。
数据字典也从"存在库里"改成"优先读文件"——客户的库是只读的，不能往里建表。
提示词里的方言随连接器切换，避免在 PostgreSQL 上生成 SQLite 专有语法。

### 决策二：为什么自己写向量索引，而不是用现成向量数据库

- **问题**：表结构检索需要向量相似度，是否引入专用向量数据库。
- **决定**：自己实现基于余弦相似度的内存索引。
- **理由**：
  1. 结课项目的表数量在几十张量级，暴力计算足够快（毫秒级），引入向量数据库属于用大炮打蚊子。
  2. 面试时"向量检索就是归一化后的点积排序"这句话，比"我用了某个向量库"有信息量得多。
  3. 依赖越少，环境问题越少，教学文档越短。
- **代价**：十万级以上向量会慢。接口保留，可替换。

### 决策三：为什么不把整个数据库结构塞进提示词

- **问题**：模型需要知道表结构，怎么给。
- **备选**：全量塞入、按需检索。
- **决定**：检索后裁剪，只给相关的 5 到 8 张表。
- **理由**：三十张表、四百个字段的结构描述约两万字，全量塞入有两个后果——超出上下文预算、且关键信息被稀释导致模型抓错表。裁剪后准确率更高、成本更低、延迟更小。
- **代价**：引入"检索可能漏表"的新失败模式。因此必须单独度量**检索召回率**，否则无法区分失败原因。

### 决策四：为什么要做外键图扩展

- **问题**：向量检索按语义相似度召回，但"语义最像的表"未必是"需要连接的表"。
- **例子**：问"复购率"，语义最像的是订单表，但正确答案需要订单表连接客户表再连接退款表。
- **决定**：召回后沿外键关系补一跳邻接表。
- **理由**：语义相似度衡量的是"像不像"，而连接需求由**关系结构**决定，两者是正交的信息。只靠向量必然漏。
- **代价**：候选表变多，提示词变长，可能引入噪声。用重排和数量上限控制。

### 决策五：为什么是"生成—校验—执行—修复"四段，而不是一次生成

- **问题**：模型生成的语句经常有错（字段名拼错、方言不符、聚合层级错）。
- **决定**：四段流水线，出错则把错误信息回喂重写，最多两轮。
- **理由**：一次生成的失败率在复杂问题上很高；而数据库返回的错误信息本身就是极高质量的反馈信号，比让模型"自我检查"可靠得多。
- **代价**：延迟和成本上升（最坏情况三次模型调用）。因此需要记录"首轮成功率"与"修复贡献率"，证明这段投入值得。

### 决策六：为什么用执行结果比对，而不是字符串比对

- **问题**：怎么判断生成的语句对不对。
- **备选**：与标准答案字符串比对、与标准答案执行结果比对。
- **决定**：执行结果比对。
- **理由**：同一个结果有无穷多种写法（连接顺序、别名、子查询与连接互换）。字符串比对会把大量正确写法判错，导致指标失真、优化方向错误。
- **代价**：需要处理结果集排序、重复行、浮点数精度；且要求标准答案本身可执行。

## 6. 模块与接口

| 模块 | 职责 | 关键接口 |
|---|---|---|
| `core/config` | 读取配置文件，支持后端切换 | `load_config(path) -> Config` |
| `core/interfaces` | 定义所有可替换组件的契约 | `Connector` / `Embedder` / `Reranker` / `VectorStore` / `Llm` / `Evaluator` |
| `core/tracing` | 全链路追踪，记录每一段的输入输出与耗时 | `Tracer.span(name)` |
| `connectors` | 数据库连接、只读沙箱、超时、行数限制 | `execute(sql) -> QueryResult` |
| `schema` | 表结构内省、数据字典合并、外键图 | `introspect() -> Schema` |
| `retrieval` | 向量召回、关键字召回、融合、重排、图扩展 | `retrieve(question, k) -> list[Table]` |
| `generation` | 提示词组装、模型调用、修复 | `generate(ctx) -> str` |
| `execution` | 校验、执行 | `validate(sql) -> CheckResult` |
| `evaluation` | 执行准确率、检索召回率、归因 | `run(dataset) -> Report` |
| `mcp_server` | 对外暴露工具 | 见第 9 节 |

配置文件形态（切换后端不改代码）：

```yaml
retriever:
  dense_top_k: 20
  sparse_top_k: 20
  fusion: rrf
  rerank: { provider: none, top_n: 8 }
  graph_expand: { enabled: true, max_hops: 1 }
executor:
  dialect: sqlite
  read_only: true
  timeout_s: 10
  max_rows: 500
```

## 7. 数据方案

### 7.1 演示库（自建）

- 24 张表，分两个业务域：
  - **订单域 14 张**：地区、客户、收货地址、类目、供应商、商品、订单、订单明细、支付、退款、物流、营销活动、评价、库存
  - **内容域 10 张**：作者、栏目、文章、标签、评论、浏览统计、订阅、邮件推送、关键词指标、广告投放
- 两个域之间**没有任何外键关联**，内容域是刻意加入的"干扰项"。只有库里有大量无关表，"该看哪几张表"才是一个真问题——如果全库只有十几张互相连着的表，检索几乎不可能出错，指标也就没有意义。
- 数据量：客户 2000、订单 2 万、订单明细约 5 万
- **随机种子固定**，任何人跑出来的数字一致，评测可复现
- 带**数据字典表**（表名、字段名、中文说明），模拟真实数仓的元数据管理

### 7.2 公开评测集（报分数用）

- **Spider**：跨领域、经典、题量充足，适合起步
- **BIRD**：规模更大、含"外部知识"字段与脏数据，更接近真实
- 做法：取子集（200 题）跑自己的管线，报执行准确率

两套数据分工明确：**公开集证明能力，自建库做演示**。

### 7.3 测试集构成（自建 200 题）

| 难度 | 占比 | 说明 |
|---|---|---|
| 单表过滤聚合 | 40% | 基础能力 |
| 多表连接 | 40% | 核心难点 |
| 嵌套子查询 | 20% | 区分度 |

每题包含：问题、标准语句、涉及的表、难度标签、考察点。

## 8. 评测方案

### 8.1 指标

| 指标 | 定义 | 为什么需要 |
|---|---|---|
| 执行准确率 | 生成语句与标准语句的执行结果集一致 | 主指标 |
| 检索召回率 | 标准语句用到的表，有多少比例进入了候选集 | 区分"检索错"与"生成错" |
| 首轮成功率 | 不做修复时一次生成正确的比例 | 衡量生成质量 |
| 修复贡献率 | 修复循环带来的准确率增量 | 证明这段复杂度的价值 |
| 平均耗时 / 平均调用次数 | 工程指标 | 成本意识 |

### 8.2 消融矩阵

| 编号 | 变量 | 观察 |
|---|---|---|
| A | 全量表结构 vs 检索裁剪 | 验证决策三 |
| B | 无图扩展 vs 有图扩展 | 验证决策四 |
| C | 无修复 vs 两轮修复 | 验证决策五 |
| D | 仅向量召回 vs 向量+关键字融合 | 验证混合检索 |
| E | 无取值样本 vs 有取值样本 | 验证取值索引价值 |

每跑一组，产出一行数字，最后汇总成一张表。这张表就是简历上最硬的部分。

### 8.3 失败归因

每一道错题标一个原因码：

- `RETRIEVAL_MISS`：需要的表没被召回
- `SCHEMA_LINK_ERROR`：表召回对了，但连接或字段选错
- `SYNTAX_ERROR`：语法错误（修复后仍失败）
- `SEMANTIC_ERROR`：能跑，但口径理解错
- `AMBIGUOUS`：问题本身有歧义，应澄清而未澄清

归因分布本身就是结论，也是面试时"你最大的失败来源是什么"的答案。

## 9. 对外工具面

| 类型 | 工具 | 用途 |
|---|---|---|
| 探索 | `list_tables(keyword)` | 模糊查找表 |
| 探索 | `describe_table(table)` | 字段、类型、说明、行数 |
| 探索 | `sample_values(table, column)` | 取值样本，解决"华东区"与库内取值的映射 |
| 检索 | `search_schema(question)` | 候选表召回（含图扩展） |
| 校验 | `validate_sql(sql)` | 语法与权限检查 |
| 执行 | `run_sql(sql)` | 只读沙箱执行 |
| 高层 | `ask_data(question)` | 一条龙：澄清 → 检索 → 生成 → 修复 → 执行 → 解释 |

**两条调用链**（本项目相对同类项目的核心差异）：

- **薄链路**：客户端模型自己调用前六个工具，自己写语句
- **厚链路**：客户端只调用 `ask_data`，检索与生成都在服务内部完成

同一个测试集对比两条链路的执行准确率、调用轮数、令牌消耗，得出"能力应该放在哪一层"的结论。这是能讲四十分钟的东西。

## 10. 里程碑

| 周 | 交付 | 验收标准 |
|---|---|---|
| 第 1 周 | 数据层 + 元数据内省 + 200 题测试集 + 最简直出管线 | 能跑出**基线执行准确率**（预计 30% 到 45%） |
| 第 2 周 | 检索层全套（向量、关键字、融合、重排、图扩展） | 执行准确率相对基线提升，检索召回率有数 |
| 第 3 周 | 校验、沙箱、修复循环、模型上下文协议服务 | 服务可被客户端调用；修复贡献率有数 |
| 第 4 周 | 面板、消融表、教学文档、演示录屏 | 一张完整实验表 + 一份能照着做的文档 |

**噪声基准**：同一配置三次运行分别 92.00 / 92.50 / 93.00，极差 1 个百分点（2 道题）。
所以差值小于 2 道题的实验，不下结论。

### 五个结论

**一、外键图扩展是贡献最大的模块（−6.50，13 道题）。**
关掉它，候选表从 7.67 张降到 5 张，准确率掉 6.5 个点。这证实了"语义最像的表，往往不是需要连接的表"：
只靠向量召回，连接所需的表根本进不了上下文。这是本项目最硬的一条因果证据。

**二、上下文太少比太多更致命（−10.00 对 −0.50）。**
只给 3 张表掉 10 个点；把 24 张表全塞进去只掉 0.5 个点（在噪声内）。
所以在 24 张表的规模上，检索的价值不在"更准"，而在**同样的准确率下省下 12 张表的上下文**。
等库大到装不下，这个价值才会变成准确率——**这是有条件的结论，不能直接说"检索提升了准确率"**。

**三、取值索引从负收益变成了正贡献（−3.00）。**
42 题时期它是 −4.76（关掉反而更好），原因是当时把所有候选表的全部取值样本都渲染进提示词，噪声盖过信号。
改成"只注入问题里出现的取值"之后，它变成 +3.00。
**这是本项目唯一一次"发现模块有害 → 定位原因 → 改设计 → 转正"的完整闭环**，也是面试最值得讲的一段。

**四、报错重写贡献为 0。**
首轮成功率 99.5%，修复循环几乎从不触发。
诚实结论：在当前模型和这批题上，这个模块没有产生价值。保留它的理由是"更弱的模型或更复杂的库会用到"，
但这句话目前没有数据支撑——**它现在的定位是"成本很低的保险"，不是"被验证有效的模块"**。

**五、混合检索的价值是边缘的（−1.50，约 3 道题）。**
只用向量召回掉 1.5 个点，正好在噪声边缘。关键字召回确实补了一点（专有名词精确匹配），
但不足以说"显著"。

**六、重排是负收益，而且越"专业"越差（重叠 −1.00，交叉编码器 −4.50）。**
两个重排器都关着用。原因查清楚了：**重排会改变图扩展的起点。**

打个比方：问"一共有多少客户"，不重排时前两名是 `customer_addresses`、`customers`；
上了交叉编码器，第一名换成了正确的 `customers`，但第二名换成了 `keyword_metrics`（内容域的表）。
图扩展从这两张出发，上下文就被带进了内容域。

所以这不是"交叉编码器不行"，而是**下游依赖了排序的语义**：重排优化的是"这张表和问题有多相关"，
而图扩展需要的是"哪张表是连接计划的入口"。两件事不是一回事。

**逐题诊断（200 题，离线重算）**：

| 指标 | 数值 |
|---|---|
| 前 2 名种子集合发生变化 | 147 题（73.5%） |
| 前 5 候选集合发生变化 | 194 题（97.0%） |
| base 对、R2 错（恶化） | 13 题，其中 **11 题种子集合变了** |
| base 错、R2 对（改善） | 4 题，全部种子集合变了 |

净 −9 道题，就是 −4.50%。**机理确认，不是运气。**

**R3 大模型重排是唯一没掉点的（93.50%，+1.00，2 道题，在噪声内）。**
差别在于它看的是"哪些表能回答这个问题"，比"相关性"更接近下游要的信号；
但 +2 道题不足以说它有效，而且每题多一次调用，所以**默认仍然关闭**。

**结论：这个架构里重排不该开。要开就得同时改造图扩展的种子选择逻辑**——
比如固定从第一名出发，或者让"入口表"和"相关表"分开打分。

### 七、把整条链路改成"适配交叉编码器"的版本，结果更差（V2 −6.00）

按上一节的判断，做了一版**为交叉编码器重写的链路**，不是只换零件：

| 改动 | 原来 | V2 |
|---|---|---|
| 顺序 | 先重排，再扩展 | **先扩展，再精排**（CE 在扩展后的池子里裁决） |
| 候选数 | 固定 5 张 | 总分阈值 + 总表数预算 |
| 扩展起点 | 排名前 2 | 排名前 3（在扩展前，不受重排影响） |

结果：**86.50%，比只换零件的 R2（88.00%）还差，比基准低 6 个点。**

关键指标是**检索召回率掉到 91.46%**（基准 99.04%）——交叉编码器把"结构上必需、但语义上不相关"的表排到了后面，
比如问"每个大区的退款金额"，它会优先保留 `orders`、`refunds`，把 `regions` 挤出去。

**根因**：`bge-reranker` 是在"问题—段落相关性"上训练的，它判断的是"这段文字能不能回答这个问题"；
而这里需要的是"这张表**能不能和其他表拼成**一条正确的查询"。**这两件事在训练目标上就不是一回事。**

**最终结论（三条，按可信度排序）**：

1. 表级重排在 24 张表的规模上不成立——三种实现（词面、交叉编码器、大模型）里两种明显掉点，一种在噪声内。
2. 掉点的机理已定位：重排改变了图扩展的起点；把顺序反过来（先扩后精排）也救不了，因为它同时降低了召回。
3. 这不是"模型不够强"，是**任务不匹配**：相关性判断 ≠ 连接可行性判断。要真解决，得训一个以"能否完成查询"为目标的排序器，而不是拿通用重排模型硬套。

### 薄链路与厚链路对比（前 60 题，同一批题）

| 链路 | 执行准确率 | 平均轮数 | 平均工具调用 |
|---|---|---|---|
| 厚链路（服务端全包） | **96.67%** | 1.0 | 0 |
| 薄链路（模型自己调工具） | **60.00%** | 4.08 | 3.25 |

薄链路里还有 10 道题在 5 轮之内没给出最终语句。

**结论：把工具交给客户端模型自己探索，准确率掉 36 个百分点，同时每次问答多花 3.25 次工具调用。**
原因很具体：模型不知道该先看哪张表（没有检索），不知道金额有三个口径（没有提示词约束），
写错了也没有修复机制。

**必须说明的局限**：薄链路用的是文本协议（`CALL 工具名(参数)`），不是原生的函数调用接口。
换成原生接口会好一些，但结构性差距还在——因为缺的是"该看哪张表"这个判断，不是调用格式。
